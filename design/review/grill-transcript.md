
## Q1 (codex)
What exact state does the verdict banner show when the deterministic plan says “6×800m today” but readiness is borderline or stale enough to suggest Easy/Rest, and how will the athlete see that this is a conflict between plan intent and data confidence rather than a single authoritative answer?

**A1 (claude):** The banner never averages the conflict away — it shows the recommendation and the dissent explicitly. State: verdict word **"Go easy"** in sand, rationale line reads *"Plan calls for 6×800m, but HRV is 12% below baseline"* — plan intent and data both named in one sentence. Below it, the session row shows the planned workout struck through to a modified version: ~~6×800m~~ → "4×800m or easy 40min," with a "Keep planned session" button so the athlete overrules us in one tap. If the driver is staleness rather than a real signal, the verdict softens to *"Likely train — last sync 14h ago"* with the amber timestamp chip, and the planned session stays unmodified. Conflict = show both sides + one-tap override; low confidence = hedge wording, never a downgraded verdict.

## Q3 (codex)
When the banner changes `6×800m` into `4×800m or easy 40min`, is that substitution generated by deterministic local rules or by Claude, and what exact on-screen evidence shows the athlete the rule/threshold that made that edit valid instead of just making the app look like an opaque coach?

**A3 (claude):** Deterministic local rules — Claude never touches the substitution. The plan engine owns a small modifier table (e.g., `HRV −10–15% below 7-day baseline → reduce interval volume 30%, cap intensity at threshold`), and 4×800m is 6×800m through that rule. Claude only *phrases* explanations; it cannot alter today's session.

On-screen evidence: the modified session row carries a small `Adjusted · rule` tag. Tapping it opens a sheet showing the exact trigger in the athlete's own numbers: "HRV 52ms vs baseline 61ms (−15%). Rule: reduce interval volume when HRV is >10% below baseline. Original: 6×800m." Same before/after row grammar as the AI plan-edit cards, but the ledger line reads **"Adjusted by rule R4 — no AI involved"** — deliberately reusing the guardrail surface so provenance is always one tap away, and rule edits are visibly distinct from Claude proposals.

## Q4 (codex)
What is the exact calibration path for rules like “HRV >10% below baseline → reduce intervals” so the app does not repeatedly downshift a healthy athlete because of normal device noise, travel, alcohol, menstrual cycle, or a bad wearable reading?

**A4 (claude):** Calibration is structural, not tuned per-athlete-guess. Three layers:

1. **Baseline is a rolling 60-day median with ±1 SD normal band**, not a 7-day mean — so the trigger is really "outside your personal normal range," and the 10% figure is replaced by `HRV < baseline − 1.0 SD` computed from the athlete's own variance. Noisy wearables get wider bands automatically.
2. **Two-signal confirmation**: a rule fires only when HRV-low is corroborated by resting HR elevated >5 bpm or sleep <6h. Single-metric outliers (bad strap night, one beer) never downshift alone.
3. **Persistence gate**: one anomalous morning produces the hedged wording ("Likely train"); the volume-reduction rule requires the signal on 2 of the last 3 days.

Overrides feed back: two "Keep planned session" taps on the same rule within 14 days widens that rule's threshold 0.25 SD, logged in the rule sheet.

## Q5 (codex)
When multiple coach proposals, deterministic readiness adjustments, and manual athlete edits touch the same week, what exact conflict model prevents an “Apply to week 6” or 7-day “Revert” action from overwriting newer plan changes or producing stale before/after diffs?

**A5 (claude):** Every plan mutation — coach apply, rule adjustment, manual edit — appends to a single per-week revision log; the week's state is derived, never edited in place. Each proposal card is pinned to the revision it diffed against (`baseRevision: 41`). On Apply, if `currentRevision != baseRevision`, the apply is refused and the card re-renders its diff against current state with a "Plan changed since this was proposed" banner — the athlete re-approves or dismisses. No silent rebase, no merge heuristics; last-approver-wins only after seeing a fresh diff.

Revert is an inverse-append, not a rollback: it creates a new revision undoing exactly revision N's delta. If later revisions touched the same sessions, Revert shows which and requires the same fresh-diff confirmation. Nothing ever overwrites unseen state.

## Q6 (codex)
What exact state does Today show when Garmin and HealthKit disagree about yesterday’s run, sleep, or HRV, and how does the athlete see source precedence and confidence without the app either hiding the conflict or turning the banner into a data-debug screen?

**A6 (claude):** One row on the verdict card, full detail one tap away. Precedence is fixed and deterministic: Garmin wins for runs and HRV (chest-strap/watch-native measurement), HealthKit wins for sleep (aggregates all sources). The banner always shows one number from the winning source — never an average, never dual values.

The conflict surfaces as a small `2 sources` chip next to the affected driver card, not on the banner. Tapping opens the same sheet grammar as rule R4: "HRV: Garmin 52ms (used) · Apple Health 61ms. Garmin is primary for HRV — change in Settings." If divergence exceeds the metric's 1 SD band, the driver card shows the amber uncertainty treatment and the two-signal confirmation layer (A4) treats that metric as unconfirmed — so a disputed HRV alone can't downshift a workout. Banner stays clean; provenance lives one tap deep, consistent with every other receipt in the app.

## Q7 (codex)
When the athlete ignores “Rest” and does an unscheduled hard run that syncs 6 hours late, what exact state does Today show the next morning, and what deterministic rule prevents the app from either moralizing the override or blindly stacking the planned quality workout on top of the new load?

**A7 (claude):** Yesterday's run enters the same revision log as any other load — no special "override" state exists. Next morning the banner reads: **"Rest — yesterday: unplanned hard run (8.2km, load 142)."** Neutral inventory, same grammar as every rationale line; the app records, it doesn't grade. No streak break, no amber, no "you ignored our advice" copy — that wording is banned from the string catalog.

The deterministic rule is the existing ACWR/load input, not a new one: the synced run raises acute load immediately on ingest, and today's planned quality session runs through the same modifier table (rule family: `acute load > threshold → swap quality for easy/rest, push quality +48h`). The rescheduled 6×800m appears in Plan as a rule-adjusted revision with the standard `Adjusted · rule` receipt: "Hard effort logged yesterday; quality moved to Thursday." Late sync changes nothing structurally — load rules re-evaluate on every ingest, so a 6-hour delay just means the adjustment lands at sync time instead of midnight.

## Q8 (codex)
If the app demotes the 78/100 score but still uses it to drive verdicts, what exact interaction teaches the athlete the score is not something to optimize or “game,” especially when Trends still shows 28-day average readiness and best readiness?

**A8 (claude):** The score never appears alone — every surface binds it to the verdict, never the reverse. On Today it renders as `readiness 78` in SF Mono caption, untinted, with no delta arrow, no "▲+4 vs yesterday," no progress framing. You cannot tap it; tapping the banner opens drivers, which are behaviors (sleep 7h40, HRV band), not the composite.

Trends is the real fix, and you've caught a flaw: "best readiness" is a leaderboard stat — it's cut. Trends shows the verdict distribution instead: "Trained 16 · Easy 5 · Rested 7," plus per-driver trends. The 28-day readiness line stays but is banded (normal range shaded), unlabeled by peaks, and captioned "readiness reflects recovery, not effort." No maxima, no records, nothing to chase.

## Q9 (codex)
Your AI edit ledger is “always visible, never collapsed,” but on a small iPhone at AX text sizes with a 6-session weekly diff, what exactly stays above the fold, what wraps or moves, and how do you prevent the guardrail chrome from burying the actual workout changes the athlete must approve?

**A9 (claude):** The ledger compresses to one line; the diff is the content. Above the fold on an iPhone SE at AX3: card title ("Week 6 proposal"), the ledger as a single row of three glyph+word chips — `sparkles Proposed · checkmark.seal Validated · person Awaits you` — then the first two or three session diff rows. Each diff row is one session: day label, ~~old~~ → new, wrapping vertically at AX sizes via `ViewThatFits` into stacked before/after lines rather than side-by-side columns. The Apply button sits pinned at the card bottom after scroll — you cannot approve without traversing every row, which is the point.

"Never collapsed" was overclaimed as chrome; the correction: the *sequence* is always present, but validation detail (n rules) moves behind the Validated chip's tap target. Three chips ≈ 44pt row even at AX5, so guardrails cost one row, sessions get the rest.

## Q10 (codex)
Where does the athlete record subjective context that wearables miss — soreness, illness, travel, heat, stress, hangover — and what exact deterministic rule path keeps that input from becoming either ignored decoration or an unvalidated self-diagnosis that can override the plan?

**A10 (claude):** A morning check-in card on Today, and its input feeds the same rule engine as any sensor — never a free-form override.

Interaction: when the athlete opens the app before today's first session, the verdict card shows one quiet row: "Anything to note?" with fixed chips — sore, ill, poor sleep, travel, alcohol, stress, heat. No free text, no severity sliders. Chips are typed signals, not diagnoses.

Rule path: each chip maps to a defined role in the existing engine. Most chips (travel, alcohol, stress, heat) act only as **corroborators** in the A4 two-signal layer — they can confirm a wearable anomaly but never fire alone. Two chips carry standalone rules because wearables genuinely miss them: `ill → rest, quality frozen 48h` and `sore (2 consecutive days) → intensity capped`. Every chip-triggered adjustment gets the standard `Adjusted · rule` receipt naming the chip: "You reported illness — rule R7." Unused chips still log to the day's record, visible in the driver sheet — recorded, never decorative. And the athlete can always overrule via "Keep planned session," same as any rule.
